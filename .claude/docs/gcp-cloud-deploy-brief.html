GCP Cloud Deploy — Architecture Brief

Status: Draft for architect review
Component: infra/gcp/ activation (Cloud Automated tier)
Mode: Build mode — architecture locked in seed document, this brief drives activation work
Repo posture: Public open-source. No client artifacts ever live in this repo.

1. Context and intent

The leansecurity-nuclei pipeline runs in two modes today: local CLI (poetry run python scanner/scan.py <client>) and local Docker. The third tier — Cloud Automated — exists as scaffolding under infra/gcp/, infra/gcp/workflows/, and deployments/_example/, but has never been validated end-to-end. The repository README explicitly states this is "not yet available."

The Terraform exists. The work is activation, validation, and operationalization — turning inert configuration into a deployed, scheduled, ephemeral scanning pipeline running in a per-client GCP project, distributed as an open-source artifact.

2. Operating model — open-source pipeline, client-hosted deployments

Public repo, private deployments

This is a public, open-source repository. It contains the reusable scanning pipeline — scanner, container image build, Terraform module, documentation. It contains zero client-identifying data.

Per-client deployment configuration — Terraform tfvars, target lists, backend configuration — lives entirely outside this repository, in client-controlled storage. There is no deployments/<client>/ folder in this repo. deployments/_example/ exists only as a template documenting what a private deployment folder should contain.

This is the standard shape for an open-source consulting product: the public repo publishes the module; consumers — including LeanSecurity's own consulting practice — reference it from private workspaces. Terraform's own ecosystem works exactly this way (terraform-aws-modules, cdk-patterns, and so on).

The operator is the architect, not CI

LeanSecurity GitHub Actions does not run terraform apply against any client project. The architect runs Terraform from a local workstation, authenticated as themselves via gcloud auth application-default login, with per-engagement scoping. The repo's CI runs lint, test, and image publishing — nothing else touches GCP.

Once provisioned, each client's scanner runs autonomously inside the client's GCP project on a Cloud Scheduler cadence. The architect's involvement ends with terraform apply. GCP itself closes the operational loop.

Scanner image distribution via GHCR

The scanner Docker image is built by the public repo's CI and published to GitHub Container Registry at ghcr.io/leansecurity/leansec-nuclei:<tag>. This is the open-source artifact. Cloud Run jobs in client projects pull from GHCR directly (or, optionally, mirror into the client's own Artifact Registry first — a per-deployment choice).

3. Runtime scan execution flow

Once provisioned, a scan run is fully autonomous if Cloud Scheduler is enabled. The scheduler fires monthly, the Cloud Run job spins up an ephemeral container pulled from GHCR (or the client's mirrored Artifact Registry), the container reads its config from GCS, runs all 7 Nuclei profiles, writes JSONL to GCS, and exits.

Three properties to note

Ephemeral. No persistent compute. The container exists only while the scan runs, then exits. The Cloud Run job definition persists; the running instance does not. This is what "no persistent infrastructure in cloud mode" means concretely.

Loose coupling to Conduit. The scanner does not know Conduit exists. It writes JSONL to a GCS prefix; Conduit's P2 ingest adapter reads from that prefix on its own schedule. The bucket is the contract.

Directory structure parity. <results-bucket>/nuclei/YYYY-MM/<profile>_YYYY-MM.jsonl in cloud mode mirrors results/<client>/YYYY-MM/<profile>_YYYY-MM.jsonl in local mode. This is what makes gcloud storage cp the trivial bridge between local and cloud — no transformation required.

4. Module flags — what's optional

The Terraform module exposes two flags that adapt the deployment to engagement model:

FlagDefaultEffect when enabledWhen to use the non-default
enable_scheduler true Provisions Cloud Scheduler job + scheduler SA + invoker IAM binding. Monthly cron fires the Cloud Run job autonomously. Disable if the client drives scan cadence from their own scheduling system (Airflow, internal CI, manual on-demand).
enable_wif false Provisions Workload Identity Federation pool, provider, and SA binding. Allows an external CI (GitHub Actions in any org) to authenticate as a GCP service account without static keys. Enable if the client wants to drive scans from their own CI, or if a future engagement model requires CI-driven Terraform apply.

The asymmetric defaults reflect what's intrinsic to the pipeline. Autonomous monthly cadence is the product; CI-driven access is a power-user extension.

What WIF provides, briefly

Workload Identity Federation lets external systems (GitHub Actions, AWS, on-prem) authenticate as a GCP service account using short-lived OIDC tokens instead of long-lived JSON key files. The trust binding lives in GCP; no static credentials exist anywhere. It's the modern replacement for service account keys.

In the default operating model, WIF is unnecessary — the architect runs Terraform from a workstation with personal gcloud credentials, and the image build pushes to GHCR with the workflow's built-in GITHUB_TOKEN. WIF earns its place only when an external system needs persistent authenticated access to the client project, which is not part of the default activation.

5. Public repo CI/CD model

The public repo has exactly two CI workflows. Both run in GitHub Actions, both touch only the public repo's own resources, neither has GCP credentials.

WorkflowTriggerActionAuth
ci.yaml Every push and PR Lint (Black, Ruff), security scan (Bandit), pytest None
publish-image.yaml Push to main touching docker/ or scanner/, and on Git tag v* Build container image, push to GHCR with :latest, :<sha>, and (on tag) :v1.2.3 GITHUB_TOKEN (built-in)

Critically: the existing infra/gcp/workflows/deploy.yml in the scaffolding is deleted, not gated. There is no client-deploy CI in the public repo. The "gated workflow" pattern from the original scaffolding is obsolete under this model — there is no per-client Terraform apply for CI to run.

GHCR image tagging

Images are tagged with three labels per build:

  • ghcr.io/leansecurity/leansec-nuclei:latest — moves with every main-branch build. For experimentation only.
  • ghcr.io/leansecurity/leansec-nuclei:<commit-sha> — immutable, traceable to source. For pinned deployments.
  • ghcr.io/leansecurity/leansec-nuclei:v1.2.3 — semantic version, set on Git tag push. The recommended pin for production deployments.

Client tfvars should pin to a semver or SHA tag, never :latest. The pin is the deliberate decision point for scanner version rollout per client.

6. Per-client onboarding

Onboarding a new client is a procedure run by the architect. It is mechanical, scriptable, and billable to the engagement.

Steps 1–4 are bootstrap: they create the trust anchor that lets Terraform run. They are codified in a runbook (scripts/bootstrap-gcp-client.sh in the public repo, or documented in infra/gcp/README.md) — not in Terraform, because Terraform itself depends on the state bucket and architect IAM access existing first.

Steps 5–7 use the engagement-specific private storage. The architect maintains a local working copy of each client's deployment folder, with the source of truth being whatever private location the engagement designates (per-client variant). When the architect needs to update a client's config — change targets, bump scanner image version — they pull, edit, apply, push back.

Required APIs (step 2)

  • run.googleapis.com — Cloud Run Admin API
  • cloudscheduler.googleapis.com — Cloud Scheduler API (only if enable_scheduler = true)
  • storage.googleapis.com — Cloud Storage API
  • iam.googleapis.com — IAM API
  • iamcredentials.googleapis.com — required for WIF (only if enable_wif = true)
  • sts.googleapis.com — Security Token Service (only if enable_wif = true)
  • artifactregistry.googleapis.com — only if the deployment mirrors the GHCR image into a client AR

IAM for the architect (step 4)

Granted at the project level by the client admin, scoped to the engagement:

  • roles/run.admin
  • roles/cloudscheduler.admin
  • roles/storage.admin
  • roles/iam.serviceAccountAdmin
  • roles/iam.serviceAccountUser

Time estimate

A clean onboarding, with the bootstrap runbook in hand and a GCP project ready, is approximately 30–60 minutes of architect time — most of it waiting for GCP API enablement and the first terraform apply. One-time per client.

7. Known defects in the scaffolding

Two defects in the existing scaffolding will surface during activation. Both are work items in the project.yaml.

7.1 Terraform env block formatting

The current infra/gcp/main.tf writes Cloud Run env blocks in a non-standard inline form: env { name = "..." value = "..." }. The google_cloud_run_v2_job resource expects each env entry as a properly-formatted multi-line block. The current file also appears to be truncated mid-resource in the project snapshot — the RESULTS_BUCKET env value is incomplete. Both need fixing before first plan.

7.2 profiles.yaml ↔ entrypoint.sh drift

The scanner Python parses profiles.yaml at runtime. The container entrypoint hardcodes equivalent flags. These must match. They don't today. The entrypoint writes files named identity_*.jsonl, transport_*.jsonl, owasp_top10_*.jsonl but profiles.yaml defines profiles identity_remote_access, transport_security, owasp_top10_core. The seed document calls this out as a bug: drift between profiles.yaml and entrypoint.sh breaks the locked design decision that directory structure stays identical across local and cloud. Must be fixed before any cloud run.

Note: the deployments/mdi/ gitignore contradiction from earlier drafts of this brief is dissolved by the operating model — no deployments/<client>/ folders ever live in the public repo, so there is nothing to gitignore. Any existing placeholder folder is slated for removal as part of activation.

8. Scope boundary for this feature

In scope

  1. Fix the two defects in §7
  2. Rewrite infra/gcp/ to:
    • Add enable_scheduler variable (default true), put scheduler resources behind count
    • Add enable_wif variable (default false), put WIF resources behind count
    • Remove the implicit assumption that the scanner image lives in a specific Artifact Registry path — accept any image URI via scanner_image
    • Make Artifact Registry repository provisioning optional behind a flag for clients who want to mirror the GHCR image
  3. Delete infra/gcp/workflows/deploy.yml (no longer applicable)
  4. Replace infra/gcp/workflows/scanner-image.yml with .github/workflows/publish-image.yaml that builds and pushes to GHCR on main and on tag
  5. Write scripts/bootstrap-gcp-client.sh — the gcloud runbook for steps 1–4 of onboarding
  6. Update deployments/_example/ to reflect the GHCR image path and the new module flags
  7. Remove the placeholder deployments/mdi/ from the repo
  8. Run end-to-end validation against a dedicated GCP test project owned by LeanSecurity
  9. Update README.md and infra/gcp/README.md to document the operating model, GHCR distribution, and module flags
  10. Update the seed document — add the locked design decisions for the public/private topology, GHCR, and the module-flags pattern

Out of scope

  • Onboarding any actual paying client. First-client onboarding consumes this feature's deliverables.
  • AWS or Azure modules. They remain stubbed.
  • Any change to scanner/ Python or tests beyond fixing the profile-name drift in §7.2.
  • Cloud-side validation requiring real client credentials. Validation runs against a LeanSecurity-owned test project only.
  • Conduit ingestion validation. The bucket contract is verified by the checklist; Conduit-side reading is its own project.
  • Tooling to manage per-client deployment folders in their private storage (sync scripts, CLI helpers, etc.). Architect manages these manually for now.

9. Acceptance criteria

Scoped to a LeanSecurity-owned GCP test project. The deployment folder for the test client lives in private storage outside the public repo, exercising the full flow end-to-end.

  1. scripts/bootstrap-gcp-client.sh executes cleanly against a fresh GCP project, enables required APIs, and creates a working Terraform state bucket.
  2. A test client deployment folder exists in private storage with main.tf, backend.tf, terraform.tfvars, targets.txt, and references the public module via a Git source ref.
  3. publish-image.yaml in the public repo successfully builds and pushes the scanner image to ghcr.io/leansecurity/leansec-nuclei with the expected three tags.
  4. terraform init succeeds against the client state bucket from the architect workstation.
  5. terraform plan shows the expected resources with no syntax errors and respects the default flags (scheduler on, WIF off).
  6. terraform apply completes without errors.
  7. Config bucket contains targets.txt and profiles.yaml.
  8. Manual gcloud run jobs execute succeeds and the container pulls the image from GHCR without auth issues.
  9. JSONL files appear in the results bucket under nuclei/YYYY-MM/.
  10. JSONL filenames match profiles.yaml profile names exactly (resolves §7.2 drift).
  11. Cloud Scheduler shows the correct next execution time.
  12. A second terraform plan with enable_scheduler = false shows the scheduler resources being destroyed; reverting shows them being recreated. Same test for enable_wif.
  13. Public repo CI (ci.yaml) passes on PR and merge throughout.

10. Open decisions for architect sign-off

Before producing the project.yaml:

  1. Image tag scheme. Use all three tags (:latest, :<sha>, :v1.2.3) as described in §5, or a subset?
  2. GHCR image name. ghcr.io/leansecurity/leansec-nuclei (matches the artifact's role) or ghcr.io/leansecurity/leansecurity-nuclei (matches the repo name)?
  3. Bootstrap script vs. documentation only. Ship scripts/bootstrap-gcp-client.sh as an executable bash script, or document the gcloud commands inline in infra/gcp/README.md only? Script is more useful for repeatability; doc-only is more visible.
  4. Existing infra/gcp/workflows/scanner-image.yml. Delete entirely, or repurpose as the basis for publish-image.yaml?
  5. Artifact Registry mirror flag name. Proposed: enable_ar_mirror (default false). If enabled, the module provisions an AR repository in the client project. The architect's onboarding then includes a step to docker pull from GHCR and re-tag/push to the client AR before terraform apply. Confirm the name and default.
  6. Locked design decisions for the seed document. Confirm wording for three new entries:
    • "Public-repo, private-deployment topology. The public repository contains the reusable pipeline and module. Per-client deployment configuration lives in client-controlled storage outside the public repository."
    • "GHCR is the scanner image distribution channel. The image is built from the public repository and published to ghcr.io/leansecurity/leansec-nuclei. Clients pull from GHCR directly or mirror into their own Artifact Registry."
    • "Cloud-side execution is architect-driven, not CI-driven. terraform apply runs from the architect's workstation against the client GCP project. Public-repo CI does not hold GCP credentials and never touches client infrastructure."

Sign off on these and the project.yaml follows.
