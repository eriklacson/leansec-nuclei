## Implementation plan

### B1 — `.claude/skills/gcp-deploy/SKILL.md`

**Structure:**
```
---
name: gcp-deploy
description: >
  Deploy the leansecurity-nuclei pipeline to GCP. Triggers on phrases like
  "deploy this to GCP", "run the GCP deployment", "apply the gcp-deploy skill".
version: 1
---
```

**Constant block** (near top, clearly labelled — change at release time):
```
DEFAULT_SCANNER_IMAGE: ghcr.io/eriklacson/leansec-nuclei:latest
```

**11 numbered workflow steps:**

1. **Detect deployment folder state** — check for `deployment.yaml` in CWD. If missing → go to step 2. If present → skip to step 3. Success: file found. Failure: offer to scaffold.

2. **Scaffold from `_example/`** — copy `deployments/_example/` contents into CWD, create `deployment.yaml` from `templates/deployment.example.yaml`, prompt operator to populate values and re-invoke. Success: `deployment.yaml` exists and operator has been prompted. Failure: `_example/` not found in repo checkout → abort with path guidance.

3. **Validate `deployment.yaml` against schema** — run JSON schema validation (python `jsonschema` or equivalent) against `schema/deployment.schema.json`. Success: valid. Failure: print offending field and stop — no gcloud/terraform calls made.

4. **Run `scripts/bootstrap-gcp-client.sh`** — invoke `<repo-root>/scripts/bootstrap-gcp-client.sh <gcp_project_id> <region>`. Check whether bootstrap is needed (ask operator if it's a fresh project or re-run). Success: exits 0. Failure: surface gcloud error, check auth, stop.

5. **Render tfvars, `backend.tf`, `main.tf`** — substitute values from `deployment.yaml` into the three templates; overwrite files in deployment folder. Each rendered file starts with a `# GENERATED BY gcp-deploy skill — do not edit` header. Success: three files written. Failure: missing required YAML field (shouldn't reach here after step 3).

6. **`terraform init`** — run from deployment folder. Success: "Terraform has been successfully initialized." Failure: surface error, check backend bucket exists (bootstrap may need re-run), module path resolution.

7. **`terraform plan -out=tfplan`** — capture full output. Success: plan generated. Failure: surface error + credentials check hint.

8. **Summarize plan in chat** — present:
   - Resources created / modified / destroyed (counts)
   - **Prominent block: IAM bindings being created** (list them)
   - **Prominent block: destructive changes** (replacements, deletions, public policies) — flag each one explicitly
   - Full plan available on request
   Success: summary presented to operator.

9. **Ask operator to confirm before apply** — explicit prompt: *"Ready to apply? Reply 'yes' to proceed or 'no' to stop."* Do not continue until unambiguous affirmative. Success: operator confirms. Failure/ambiguous: stop; do not apply.

10. **`terraform apply tfplan`** — only after step 9 confirmation. Success: "Apply complete!" Failure: surface error, note partial state risk, advise `terraform show`.

11. **Report results** — list what was deployed (Cloud Run job name, scheduler if enabled, GCS bucket names), print next steps (push first scan manually, verify scanner SA IAM, if AR mirror enabled: push image to AR).

**Error handling clauses** (one per failure mode):
- YAML validation failure → step 3 stop, field-level error, no cloud calls
- `gcloud auth` missing → detected at step 4 or step 6; print `gcloud auth login` + ADC note
- `terraform` not installed → detected at step 6; print install link
- Bootstrap script failure → step 4; surface gcloud error, re-run after fix
- `terraform init` failure → step 6; check backend bucket + credentials
- `terraform plan` failure → step 7; surface error verbatim + credentials hint
- `terraform apply` failure → step 10; surface error; note state may be partially applied, advise `terraform show` + manual cleanup if needed

**Idempotency section:** Re-running regenerates all three files from YAML (idempotent overwrite). `terraform apply` on an unchanged YAML produces zero-change plan. Operator must still confirm.

**Out of scope section** (mirrors spec): first scan trigger, JSONL verification, image rebuild, module changes, multi-cloud, CLI program, backup/sync.

### B5 — `main.tf.tmpl` + `backend.tf.tmpl`

**`main.tf.tmpl`:**
```hcl
# GENERATED BY gcp-deploy skill from deployment.yaml — do not edit directly.
# Re-running the skill regenerates this file.

module "nuclei" {
  source = "../../infra/gcp"

  project_id    = var.project_id
  client_name   = var.client_name
  scanner_image = var.scanner_image
  targets_file  = var.targets_file

  enable_scheduler = var.enable_scheduler
  enable_wif       = var.enable_wif
  enable_ar_mirror = var.enable_ar_mirror

  region            = var.region
  schedule_cron     = var.schedule_cron
  schedule_timezone = var.schedule_timezone
}

# Passthrough variable declarations so `terraform plan` can resolve tfvars.
variable "project_id"       { type = string }
variable "client_name"      { type = string }
variable "scanner_image"    { type = string; default = "{{default_scanner_image}}" }
variable "targets_file"     { type = string }
variable "region"           { type = string; default = "asia-southeast1" }
variable "schedule_cron"    { type = string; default = "0 2 1-7 * 0" }
variable "schedule_timezone"{ type = string; default = "UTC" }
variable "enable_scheduler" { type = bool;   default = true }
variable "enable_wif"       { type = bool;   default = false }
variable "enable_ar_mirror" { type = bool;   default = false }
```

**`backend.tf.tmpl`:**
```hcl
# GENERATED BY gcp-deploy skill from deployment.yaml — do not edit directly.
# Re-running the skill regenerates this file.

terraform {
  backend "gcs" {
    bucket = "{{gcp_project_id}}-tfstate-leansecurity-nuclei"
    prefix = "nuclei-scanner"
  }
}
```

Backend bucket name `{{gcp_project_id}}-tfstate-leansecurity-nuclei` matches the
bootstrap script's default (`${PROJECT_ID}-tfstate-leansecurity-nuclei` at line 62 of
`bootstrap-gcp-client.sh`).

## Assumptions

1. `wif_github_repository` is included in tfvars template as a commented-out optional
   (empty string default means it's harmless when `enable_wif = false`).
2. `profiles_file`, `results_retention_days`, `results_delete_days`, `job_memory`,
   `job_cpu`, `job_timeout` are not surfaced in `deployment.yaml` schema — they remain
   module-level defaults. Operators who need to override them do so by editing the rendered
   `main.tf` directly (advanced path, documented in SKILL.md out-of-scope section).
3. The skill's substitution logic uses Python (`python3 -c` one-liner or inline script)
   as it is already present in the container and on most operator workstations. Falls back
   to `sed` if Python is absent — SKILL.md documents both.
